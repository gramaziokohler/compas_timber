What it produces

Three outputs, for three different consumers.

Give it a TimberModel with joints. It gives back an order to build in, a direction to come in from for each beam, and an honest list of the parts a robot cannot place.

Assembly order
list of element ids
first placed → last
Insertion vector
unit Vector per beam
consumed by compas_fab
Hand-placement set
set of element ids
a real shop instruction

Those three go to three audiences, in priority order. Robotic assembly is the demanding one: compas_fab takes the unit insertion vector and plans a trajectory along it, with the approach distance fixed and short and decided downstream. Visualization in Grasshopper shows the order and the arrows. Human fabrication reads the hand-placement list off the drawing.

The design premise

Every design has exceptions. The tool's job is to get close and make the exceptions easy to express — not to be right unaided. Both the order and the hand-placement set are user-overridable inputs as well as outputs, and re-running with an amended set is the intended workflow.

Two packages, one boundary

Why the algorithm code cannot see a beam.

The work is split across two top-level packages that ship in the same wheel:

  • assembly_sequencing/ — the algorithms. Cones, graphs, search. Depends on compas.geometry and nothing else. No numpy, no scipy, Python 3.9 syntax so it runs under Rhino's CPython.
  • compas_timber/planning/sequencing.py — the adapter. The only place the two meet.

The dependency runs one way only, and it is enforced structurally rather than by convention: compas_timber imports assembly_sequencing, so any import back would be circular and fail immediately. The boundary defends itself.

That matters because of what it buys. Everything the algorithms are allowed to know passes through one object, SequencingInput. Which means the solver can be tested against about twenty lines of hand-written literals — no model, no Rhino, no joint classes. When a sequence comes out wrong, you can ask whether the geometry was wrong or the search was wrong, and get separate answers.

Why those two are callbacks

constraints(element_id, active_neighbor_ids) has to be a function because an n-ary joint's constraint on one member depends on which other members are still present. A ball node with five beams leaves its sixth member very different freedom depending on how many have already come out. A per-joint lookup table cannot express that; a two-element joint is just the degenerate case.

path_is_clear(...) has to be a callback because the swept collision check needs the geometry of every element in the model, and benefits from the host's spatial index. Keeping it behind a callback leaves geometry where it belongs and keeps the algorithm package geometry-light.

The solver: the shared core

One question, asked hundreds of times: can this element get out of here, and which way?

Everything downstream is built on a single primitive. Given a set of constraints on one element, find the best direction to pull it out — or prove there isn't one. It is pure geometry: dot products and cross products, no model, no state.

The two constraint types

A joint describes the freedom it leaves a member, assuming every other member of that joint is frozen. Two types cover the whole vocabulary:

TypeMeansTestProduced by
HalfSpace(n)3‑DOF. Travel anywhere in the half-space.n · d >= 0butt joints, laps, pockets
SignedAxis(d)1‑DOF. Travel along exactly one direction.axis · d = 1mortise-tenons, dovetails, seat cuts
Signed, not bidirectional

A SignedAxis permits one direction. Its reverse pushes deeper into the joint. The solver never tests the reverse — if the permitted direction runs into material, the element is locked, and two anti-parallel axes are a genuine deadlock rather than a sign mistake. This is the most surprising part of the protocol and it is easy to "fix" into a bug.

Anything else raises. An unrecognised constraint is never dropped silently, because a dropped constraint makes an element look more free than it is — failure in the direction that hurts when a robot is holding the beam.

The three states

The solver maximises the worst-case clearance over all constraints:

maximise   min_i (n_i · d)
subject to |d| = 1

The result of that minimum is the margin: the sine of the angle by which the chosen direction clears its nearest constraint boundary. The margin then classifies the fit into one of three states.

Margin classifies; it never rejects

A beam dropped vertically into a slot between two others has a margin of exactly zero — the only feasible direction is precisely parallel to both contact faces. That is a correct answer about a genuinely tight fit, not a numerical artifact, and it must not be reported as a lock. tight is feasible.

Report the angle as a number where a human will read it. "3.2°" tells a fabricator something; "tight" does not.

How the direction is chosen

The optimum of a polyhedral cone lies on one of its extreme rays, so the solver enumerates a finite candidate set and takes the argmax — not the first candidate that happens to pass. Candidates are: each constraint normal, both signs of every pairwise cross product, and the normalized sum of all normals as an interior seed.

Two consequences worth carrying around:

  • Two half-spaces never pin down a direction. They leave a wedge, and the answer is the bisector, not the cross product. You need three to pin a ray. If a joint should produce exactly one direction, it should be returning a Line (a SignedAxis) — half-spaces bound a region, and a region with one member is a different constraint type.
  • Anti-parallel normals are handled explicitly. Their cross vanishes and the feasible set collapses into the plane they share — a beam housed between two parallel faces, which can still slide anywhere in that plane at exactly zero margin. The solver adds a basis of that plane so the case reports as tight rather than locked.

Where margins tie exactly, four further keys settle it: alignment with the interior seed (the "most centred" direction), then alignment with world up, then the rounded components for pure determinism. The world-up term is a gravity-friendly preference among directions the geometry genuinely cannot distinguish.

Then the collision check

Joint constraints only see jointed neighbours. In a dense lattice a beam can be perfectly free according to its joints while its extraction path drives straight through a beam it is not jointed to. So after the cone solve, candidates are offered in descending margin order to a swept broad-phase check against all remaining elements, and the first that clears wins.

The check sweeps the element's oriented bounding box a fixed short distance (default 100 model units) and tests axis-aligned overlap. Broad-phase, so a reported collision may be a false alarm while a reported clearance is trustworthy — erring toward "obstructed" is the safe direction for a robot.

What happens with zero constraints

An element with no active joints is entirely free, and the solver returns a roomy solution pointing up with margin 1.0. This is worth stating because the previous implementation returned None here, which also meant "locked" and "not computed" — three unrelated outcomes sharing one value. None is retired from this package's vocabulary.

The pipeline at a glance

Eight stages, and one subroutine called from two of them.

Stage 01

Collect and classify

Decide what is being sequenced, and say out loud what is not.

The adapter walks every element in the model and sorts it into one of two buckets. Beams are sequenceable. Everything else — plates, panels, fasteners, group containers — goes into excluded, each with a reason string attached.

Beams only, stated out loud

Sequencing a plate would need a different notion of insertion than "slide a stick along a vector". The earlier implementation silently gave non-beams a height of 0.0, which sank them to the bottom of the ranking while looking like a real measurement. They were still sequenced, just wrongly. Excluding them with a reason is the honest version of the same limitation.

Excluded elements are invisible to the joint kinematics but are still treated as physically present by the collision check. That is the conservative reading: a plate you are not sequencing can still be in the way.

Stage 02

Flatten to the boundary

Everything the algorithms will ever know, assembled once.

The adapter builds the SequencingInput. Element ids are str(guid), sorted, so ordering is stable across runs.

FieldWhat it is
element_idsevery sequenceable beam, in a stable order
neighborsjointed adjacency, forcibly symmetrized
base_zz of the beam's lowest point
centroid_zz of the beam's midpoint
lengthcenterline length
groupsuser-declared model groups, which always win over inferred ones
constraintscallable — asks the joints, live
path_is_clearcallable — the swept collision check
excludedid → reason, carried through to the report

Construction validates hard. Duplicate ids, an asymmetric neighbour map, a missing height — all raise. A missing height is an error rather than a default, for the same reason as above: a silent 0.0 looks like a measurement.

Where constraints actually come from

When the solver asks for constraints on a beam, the adapter walks that beam's joints, skips any joint whose other members have all been removed, calls joint.get_kinematic_constraint(beam), and converts the result: a Line becomes a SignedAxis, a Vector becomes a HalfSpace, a list becomes both. Anything else raises.

The permissive fallback

The base Joint.get_kinematic_constraint returns a single half-space pointing roughly midpoint-to-midpoint, which almost always yields a valid extraction. A large share of the joint library still inherits it, and you cannot tell "computed" from "nobody implemented this joint" by looking at the value.

So constraints from the fallback are tagged inferred and counted. Check result.inferred_total before you trust a surprising sequence — some apparent design quirks turn out to be missing implementations.

Stage 03

Normalize the overrides

Never drop a fabrication instruction someone typed without saying so.

Before any geometry runs, the two user-supplied override channels are cleaned against the model as it now stands. A hand-placed element that has since been deleted, a pin pointing at a position that no longer exists, two pins claiming the same slot — each becomes an entry in a StalenessReport that travels with the result.

Pins are also converted here from the caller's assembly-order view into the disassembly step the search actually works in: step = total - 1 - assembly_index.

Stage 04

Build the blocking graph

One edge means one thing: B must come out before A, in every possible order.

For every jointed pair, the solver is asked a deliberately narrow question: delete the entire rest of the model, leaving only A and B — can A get out? If it cannot, draw the edge A → B.

That narrowness is what makes the edge trustworthy. A larger active set can only add constraints, never remove them, so if B alone locks A, no order in the universe frees A while B is present. The edge is an unconditional precedence.

The tempting stronger rule — draw an edge to every neighbour involved in locking A in the complete assembly — is unsound, and the reason is worth internalising.

Stage 05

Intrinsic locks and subassemblies

The one distinction that decides what gets printed on a shop drawing.

Run Tarjan's algorithm over the blocking graph. Any strongly connected component with more than one member is a mutually blocking cluster: every member transitively blocks something that blocks it back, so no member can go first and no order exists that frees them.

Intrinsic lockOrder-dependent lock
MeansLocked in every orderLocked given what is still in place
Canonical casedouble birdsmoutha beam boxed in by a bad choice three steps ago
Foundup front, stage 05during search
Responseflag for hand placementroute around it
Goes on a drawing?yesnever

Keeping these apart is the whole reason the stage exists. When both produced the same warning flag, a merely mis-ordered element was indistinguishable from one that physically needs hands — and the shop floor got told to hand-place something a robot could have managed.

Sound, but not complete

Every cluster reported here really is locked forever, because every edge is an unconditional pairwise precedence. But an interlock that only closes across three or more elements at once — each pair separable, the trio not — leaves no pairwise edge to find, so it is not reported here. Those surface later as a stuck report, which is the honest outcome: the tool did not find an order, rather than claiming none exists.

Subassemblies come free

The same components double as real, geometry-derived subassembly groups, used later as a ranking preference. User-declared model groups win where they exist; otherwise each SCC is a group; otherwise an element is its own.

Every label derives from element ids, never from iteration order. That is not fussiness: the label propagation this replaced broke ties on (count, guid), and since guids are random, subassembly labels differed between runs on identical input. Non-deterministic output from a fabrication tool is a correctness defect.

Stage 06

Beam search over disassembly

Take it apart, then read the tape backwards.

The search runs on disassembly, not assembly, because an element's freedom is decided by what is still around it — and that shrinks monotonically as you take things apart. Searching forward through assembly would mean reasoning about elements that are not there yet.

Five partial sequences are carried at a time. At each step, for each partial:

  1. Assess the state. Find the grounded elements (everything at the lowest base_z), then run one articulation-point pass to find every element whose removal would strand part of the assembly from the ground. One pass answers this for all candidates at once.
  2. Filter — the hard gate. Solve each remaining element against the current active set. Feasible elements pass. Hand-placed elements pass regardless, because a person can rotate, tilt and spring a member into place and robot kinematics do not apply. Everything else is recorded with its blocking reason.
  3. Honour pins. If a pin claims this step, it becomes the only candidate. If it cannot be honoured, this partial dies with a conflict report.
  4. Rank — the soft preferences. Score the survivors and take the best few.
  5. Prune. Merge partials that have removed the same set of elements by any route, then keep the five best overall.
Hard constraints filter; soft preferences rank

Steps 2 and 4 are deliberately separate mechanisms. The earlier implementation blended five booleans and five continuous values into one lexicographic comparator, which meant a genuine constraint violation could be outvoted by an ordering accident. Splitting them is what makes the behaviour explainable, tunable and testable.

The default ranking

Gravity: bottom-up assembly is top-down disassembly. The score is a tuple, most significant term first.

#TermWhy it sits there
1Does not strand anythingthe one term whose violation produces obvious nonsense, so it leads
2base_z, descendingtake the high things off first
3centroid_z, descendingseparates beams that start at the same level
4Roomy before tightspend the free extractions while there is still room
5Subassembly continuityfinish a cluster before starting another
6Chain continuityprefer a neighbour of the last one removed
7Length, then low connectivitylong and peripheral members come off first

Terms 2 and 3 are separate lexicographic keys, not a sum. Centroid alone ranks a ground-standing post as "high"; base alone cannot separate two beams starting at the same level; adding them produces a quantity with no physical meaning and no nameable unit. The strategy is injectable — gravity is the default, not the only thing the package can express.

What happens at a dead end

There is no backtracking

When every partial dead-ends at the same step, the search returns the best partial order it reached plus a stuck report: the step index, the elements still in place, and the specific blocking reason for each one. result.is_complete goes false.

This was a deliberate trade. Beam search is deterministic, degrades gracefully instead of falling off a node-budget cliff, and makes "show me three alternative sequences" nearly free. The price is that a bad choice early cannot be undone.

If you hit a stuck report, work through it in this order:

  1. Check inferred_total first. A stuck model is often a missing joint implementation, not a search failure.
  2. Widen the beam. width=20. One argument, linear cost, often enough.
  3. Read the report and pin your way past it. This is what the override channel is for.
  4. Suspect a three-way interlock that the pairwise graph structurally cannot see.
Stage 07

Reverse and negate

Two lines that turn a teardown into a build.

The disassembly order is reversed to give assembly order, and each extraction direction is negated to give an insertion vector. A beam that pulls out along +Z goes in along -Z.

The result object is assembled here: the order, the per-element solution, the effective manual set, a proposed manual set for the next run, the intrinsic lock clusters, the subassembly labels, the excluded elements, the staleness report, and any stuck or pin conflict.

Stage 08

Write back to the model

Four attributes per element.

AttributeHolds

insertion_vectorunit Vector, or None if hand-placed and locked
requires_manual_assemblythe hand-placement flag — serialized with the model
extraction_stateroomy tight locked

The first three are also mirrored onto the graph node, which is what TimberModel.assembly_sequence reads. That reaches into the model's private graph — in one place, on purpose, and documented, because there is no public node-attribute setter. A public API for it belongs upstream in the model.

Overrides in practice

Two channels, easy to confuse, different in kind.

Hand-placement setPinned order
Says"a person places this""this goes at position N"
A fact aboutthe designa particular build
Liveson the element, serializedpassed per run, never stored
Effectexempt from the feasibility filterforces position
If impossible—reported as a conflict, never worked around

The intended loop is a conversation, not a single shot:

  1. Run it. The solver proposes a manual set — intrinsic locks, plus tight fits as candidates.
  2. You amend it, using what you know about the design that the model does not encode.
  3. Run it again with the amended set as a given. Same inputs give the same outputs; the process is idempotent.

A pin does two things, and the second is the subtle one: it claims its own step, and it forbids every other step. Without that, ranking could spend the pinned element early and the pin would fail later with the useless message "already placed".

Pins win

If a pinned position cannot be honoured, sequencing stops and reports the position, the element and the reason. It does not quietly reorder around a plan someone typed.

Where it fails

Accepted limitations. Tell people these before they discover them.

  • Cone feasibility is infinitesimal freedom. The solver proves an element can begin to move, not that it can travel far enough to clear the assembly. The swept check mitigates this over the fixed approach distance; it does not close the gap for deep mortises, scarfs or long engagements.
  • No clearance distance. Maximum travel before collision is expensive to compute and the approach distance is fixed and short downstream, so it is deliberately not answered.
  • The robot is not a point. Gripper and arm collision with already-placed elements is compas_fab's domain. A sequence certified here can still be unbuildable for reach reasons — and users will experience that as this tool being wrong.
  • Monotone sequences only. No assemble, disassemble, reassemble.
  • Stability is a proxy. "Does not strand anything from the ground" is a topological connectivity test, not a structural calculation. A piece that stays connected can still tip over.
  • Broad-phase collision. Axis-aligned bounds around a swept oriented box. False collisions are possible; reported clearances are trustworthy.

Reading a result

result.order              # element ids, first placed to last
result.insertion_vectors  # id -> unit Vector (None if locked)
result.is_complete        # False if stuck or a pin conflicted
result.state(id)          # 'roomy' | 'tight' | 'locked'
result.manual_set         # what was exempt on this run
result.proposed_manual_set# feed this back in after amending
result.intrinsic_locks    # list of frozensets
result.inferred_total     # how much of this was a guess
result.describe()         # human-readable, per element
Two habits worth forming

Check is_complete before trusting an order, and check inferred_total before trusting a vector. The first tells you the search finished; the second tells you how much of the geometry was actually computed rather than assumed.
